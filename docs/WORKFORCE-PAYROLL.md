# Workforce and Payroll — preview foundation

This branch adds a disabled-by-default, authenticated, stateless synthetic preview to the existing Worker. It does not collect employee identities, SSNs, bank details, real timesheets, tax forms or payroll data. It cannot submit payroll, transfer funds or change Stripe or JBH configuration.

## Routes (private app-server access)
Use the existing verified visitor-scoped JussPay bearer identity. Set WORKFORCE_PREVIEW_ENABLED=true only in an authorized test environment. No public browser CORS or payment activation is added.
- GET /workforce/overview: exact module readiness, no invented employee or provider records.
- POST /workforce/preview: fictional regularMinutes, overtimeMinutes, hourlyCents only; integer cents; illustrative US-style 1.5x overtime, not jurisdiction-specific payroll or net pay.
- GET /workforce/tools: read-only agent tool definitions.
- POST /workforce/tools/call: name and arguments, restricted to workforce_overview and preview_payroll. This is an internal API contract, not an MCP transport or registered ChatGPT app.

## Remaining end-to-end gates
1. Existing branded frontend: add protected Workforce navigation, People, onboarding, time approvals and payroll views. Do not replace the existing visual canon. Frontend repository is not identified by this change.
2. Establish server-side company memberships and scoped owner/payroll admin/employee roles. Verify role revocation, company isolation, minimum data collection, retention and provider-hosted sensitive onboarding. Never trust a client-supplied tenant or role.
3. Use an approved payroll provider's demo environment first. Gusto Embedded offers company/employee onboarding, payroll and filings; commercial and security approval precede production. Keep provider credentials in private secret storage and bind company IDs to authenticated company membership server-side. Do not use an account-wide token for unrestricted tenant access.
4. Implement provider-calculated preview, immutable approval tied to exact company/payroll/version and digest, expiry, idempotency, distinct approver policy, provider-side submission and verified reconciliation. Never treat a network timeout as proof of failure or repeat unknown financial side effects. Verify webhook signatures and re-read authoritative provider records.
5. Create an authenticated MCP server for read-only summaries and draft previews with user consent and scoped OAuth. Never return tax IDs, bank data or raw employee details to agent tools. ChatGPT listing and provider approval are separate gates.
6. Run focused and full repository tests, staging browser checks, provider demo reconciliation and tenant-isolation tests before any production review. This branch alone is not proof of production readiness.

References: https://docs.gusto.com/embedded-payroll/docs/getting-started and https://embedded.gusto.com/product/payroll-api.

## Private MCP demonstration
The additional POST /workforce/workspace/mcp-demo route is disabled unless both workforce preview and MCP demo flags are explicitly enabled. It uses the existing verified identity and WORKFORCE_ACCESS role lookup on every request. It implements a limited 2025-11-25 JSON-RPC message adapter for initialize, ping, tools/list and tools/call; this is not a full Streamable HTTP implementation, OAuth resource server, or registered ChatGPT plugin. No real payroll data or submission is exposed. Use the official MCP SDK and OpenAI OAuth guidance for a production transport; verify current protocol compatibility, consent, metadata discovery, token scope/audience, origin checks, and deployment before registration. See https://developers.openai.com/plugins/build/auth and https://developers.openai.com/plugins/build/mcp-server.

## Synthetic membership authority
The separate private-only configuration `wrangler.workforce-access.jsonc` is disabled by default with an empty membership list. The access worker is a local/demo fixture, not persistent HR data storage or a production authorization authority. Its sole caller must be the trusted JussPay backend via a private service binding named WORKFORCE_ACCESS in an isolated preview environment. Never expose this worker publicly: it accepts an already verified subject from the backend, not an end-user credential. No service binding was added to the production configuration. For a synthetic test, configure WORKFORCE_ACCESS_MODE=synthetic_preview and explicit expiring grants with subject, companyId, role, expiresAt (Unix seconds); use fictional test identities only. Ambiguous or expired memberships deny access. The returned grant expires within 60 seconds. Do not enable this adapter with real employee or payroll data; production needs persistent server-owned memberships, revocation, tenant selection, and independent provider authorization.

## Synthetic approval ledger
GET /workforce/workspace/records and POST /workforce/workspace/records/time-approval require verified identity, company membership, WORKFORCE_RECORDS_ENABLED=true, and a WORKFORCE_RECORDS Durable Object namespace bound to WorkforceDemoBook. The latter accepts exactly exampleId, status (approved or pending), and expectedVersion; it denies reviewers and stale writes. The object stores only fixed fictional example IDs, approval states, version and bounded transition receipts. Updates use a storage transaction and namespace selection derives solely from the trusted company grant. The production Wrangler config and migrations are unchanged: the required namespace and migration must be configured in a separate authorized staging environment before runtime tests. The existing /workforce/workspace/payroll and agent tools still use fixed example records; they are not synchronized to this demonstration ledger. This is not a production workforce database, payroll audit trail, or provider integration. Local tests use an in-memory storage and namespace double; Cloudflare transaction semantics, actual persistence and complete Worker routing require staging evidence.
