# JussPay

Cloudflare Worker billing foundation for Juss&Co. **Not live or activated.** The five catalog product mappings in `catalog-receipt.json` are inactive; no approved prices or fulfillment contracts are configured. This repository implements payment orchestration and access records; it does not implement the five applications themselves.

## Runtime contract

- `GET /catalog`: the five named products, with unconfigured products explicitly unavailable. Configured offers report `requires_provider_validation`, never a claim of provider-ready availability. Returns no invented prices.
- `POST /checkout`, JSON `{ "product": "promptos" }`: authenticate the visitor, validate an approved recurring Stripe price and expanded active product against server-owned mapping/amount/currency/interval, create or reuse customer/session, return hosted Checkout `url`.
- `POST /portal`: authenticate the visitor and return their own Stripe-hosted billing portal URL.
- `GET /entitlements`: authenticate the visitor and return only their current unexpired approved access records. Each product's backend must enforce these records before serving paid functionality; a hidden button is not authorization.
- `POST /webhook`: verify the **raw body** HMAC, five-minute timestamp tolerance, event mode/account, and customer identity. Serialize each customer's work in one Durable Object using a settled per-instance Promise queue (not a long-running `blockConcurrencyWhile` callback), retrieve authoritative subscription state, and atomically write processed-event receipts and access. Non-active subscriptions and removed/unknown prices grant no access. An old delivery cannot restore a canceled current subscription.
- The only implemented refund/dispute policy is an account-wide access hold; subsequent subscription events cannot clear it. **Sales require explicit `APPROVED_REFUND_POLICY=account_hold`; there is no default approval.** The founder must select this policy or a narrower policy must be implemented before activation. Signed revocation events continue to process independently of sales configuration, charging capability, frontend origin and AUTH availability. Manual founder review resolves holds; no automatic prorated refund policy is promised.
- Checkout return URLs never grant access. Subscription updates/cancellation are delivered by Stripe webhooks. Access expires at the stored paid period end even when renewal events are unavailable.

No ambient-cookie authentication or browser CORS is provided. Product servers call JussPay using a visitor-scoped Bearer token. `AUTH` must be a **private service binding** implementing `POST https://auth.internal/verify`, validating that token against the actual app/session identity, and returning `{ "subject": "stable-global-user-id", "audience": "jusspay", "expiresAt": 1234567890 }`. The subject must be globally unique across all five apps. Tokens must expire and the auth service must deny inappropriate issuers, audiences, revoked sessions and tenants. Never forward an unverified `x-user-id` header or founder credentials.

## Activation gates

1. Approve each product's actual paid benefits, delivery backend, currency, full recurring price, tax/refund/cancellation/privacy terms. PromptOS's known $1 first month is **not** enough to choose its renewal amount. This version has no introductory-discount automation; do not enable a normal recurring price as a substitute for that offer.
2. Create approved prices in the selected Juss&Co Stripe account, activate the catalog products, and configure the billing portal. Set `APPROVED_PLANS` to a JSON object keyed by `promptos`, `chief`, `thinktank`, `sol`, `fcr`. Each approved entry must include `approved: true`, `priceId`, `unitAmount` in minor currency units, `currency`, `interval` (`month` or `year`), `termsUrl` and nonempty `entitlements`. The runtime does not create prices or silently change commercial terms. Confirm product/price mappings in Stripe before deployment.
3. Configure real `AUTH` service binding and the product backend entitlement checks. An optional concrete Supabase adapter is included in `src/auth-supabase.mjs`, with a separate private-only `wrangler.auth.jsonc`; no real project, key or binding is configured. It sends the exact Bearer token to the configured fixed HTTPS `/auth/v1/user` endpoint and authorizes only after that provider confirms the user. Issuer, authenticated audience/role, user ID, non-anonymous identity and expiry must match. It never trusts user-editable metadata, logs tokens, forwards redirects, or caches verification. Set the adapter's `SUPABASE_URL` to the exact project HTTPS origin and securely configure `SUPABASE_API_KEY`, then bind it privately as `AUTH`. Issuer-qualified user IDs prevent different projects' identical IDs colliding. The actual apps must use this same canonical identity. Supabase token verification alone does not guarantee immediate session revocation after logout: configure short expiry and add a session revocation check if required before payment operations. Adapter compatibility with existing portfolio auth remains unverified. Set `APP_ORIGIN` to the exact HTTPS frontend origin that owns `/account`. No arbitrary client return URLs are accepted.
4. Through secure deployment configuration, set `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_API_VERSION` (reviewed pinned Stripe API version) and `STRIPE_LIVE` (`false` in sandbox, `true` only for the selected live account). Never put keys in git or chat. This is a direct merchant-account integration, not Connect. Live runtime checks `/v1/account` against `acct_1U4xNyRs4gw4sfJH`; only new checkout also requires `charges_enabled` and `details_submitted`. Existing portal and signed revocation processing continue when charging is disabled. Sandbox additionally requires a separately verified `TEST_STRIPE_CONFIG` JSON object with `approved: true`, its real `accountId`, an auditable nonempty `verificationReceipt`, and `products` mapping the product keys to actual test product IDs. No sandbox IDs are guessed from live IDs. Each approved sandbox plan must have its corresponding mapping. Test and live requests route to separate Durable Object identities (`test:` / `live:`), even for the same user.
5. Deploy the Worker and its SQLite-backed Durable Object migration using the reviewed Wrangler config. It intentionally has **no public route** and `workers_dev: false`; choose and verify the owned host before adding a route. There is no D1 migration to apply. Preserve Durable Object data on rollback. Never rename `BillingAccount` or its binding without a data migration.
6. Configure a **snapshot** webhook endpoint for this handler, aligned with the pinned API version: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `customer.subscription.created`, `.updated`, `.deleted`, `invoice.paid`, `invoice.payment_failed`, `charge.refunded`, `charge.dispute.created`. This handler explicitly consumes snapshot event objects, retrieves current subscriptions instead of trusting their old snapshots, and is not a generic thin-event handler. Stripe recommends thin events for new integrations; moving to thin events requires a separate handler contract. Unrelated account customers without JussPay metadata are acknowledged and ignored.
7. Verify in Stripe sandbox with real app auth and a deployed DO: successful purchase and feature delivery, declined payment, duplicate/reordered/retried events, async payment, cancellation at period end and immediate cancellation, portal ownership, refund/dispute suspension, expired token, two-user isolation and app enforcement. Retry failed webhook deliveries after recovery. Checkout stores a per-attempt idempotency key and offer fingerprint before its Stripe side effect. Retry with the same key only while its outcome is unknown, the offer has not changed and the attempt is under 23 hours old. Otherwise `checkout_reconciliation_required` blocks payment: inspect Stripe by stored key/customer, recover the created session into its receipt or establish that no session exists before replacing the attempt. Never erase an unknown attempt to retry. A changed approved offer expires an old open session before replacement. A completed session is reconciled against current subscription state; only `canceled` or `incomplete_expired` permits a new purchase. Active, past-due, unpaid, paused and incomplete states cannot create duplicate subscriptions. Webhook handler returns success only after atomic storage. Delivery failures remain visible in Stripe; no asynchronous queue is configured. Verify costs/rate limits and load before scaling.
8. Reconcile subscriptions in Stripe and local state after outages. A read may remain stale until the paid period ends if a cancellation webhook is lost; run reconciliation before trusting billing after incident recovery. Live end-to-end proof and account capabilities are not established by local tests.

`GET /health` is configuration-only and always reports `livePaymentsVerified: false`. It does not make network requests or establish live payment readiness.

## Local verification

`npm test` runs deterministic signature, trust-boundary, access, replay, refund, and revocation tests with an in-memory storage double. `npm run check` checks JavaScript syntax. No dependencies are required. Pinned GitHub CI runs the same two commands without a dependency install or deployment. These checks do not substitute for real Cloudflare Durable Object transaction/concurrency tests, Stripe test-mode events or browser checkout.
